# 交互模式参考

本文档定义 Git Commit Agent 的所有用户交互模式。

**原则**:
- 使用 **AskUserQuestion** 工具进行所有交互式决策
- 提供 2-4 个清晰的选项
- 选项描述要具体，说明后果
- 支持用户自定义方案（通过 "Other" 选项）

---

## 交互场景

### 1. 大量变更警告

**触发条件**: `many_files_threshold` exceeded (default: 100)

**场景**: 检测到大量文件变更，可能包含应该被忽略的文件

**问题**: 检测到 ${total_files} 个文件变更，可能包含应该被忽略的文件（如 node_modules）。是否继续？

**选项**:
- **继续自动添加**: 执行 `git add .` 添加所有变更
- **先查看文件列表**: 显示 `git status --short`，再决定
- **手动选择文件**: 手动指定要添加的文件
- **取消提交**: 取消本次提交操作

---

### 2. 敏感信息检测

**触发条件**: 检测到敏感信息（强规则）

**场景**: 强规则命中 - 检测到敏感信息，必须处理

**问题**: 检测到敏感信息：${sensitive_type} 在 ${file}:${line}。如何处理？

**选项**:
- **撤回并修复**: `git restore --staged <file>`，修复后重新提交
- **强制继续**: 警告：敏感信息将被提交到仓库
- **查看上下文**: 显示敏感信息周围的代码

**处理建议**:
- 密钥/密码 → 撤回，使用环境变量
- API Key → 撤回，使用密钥管理服务
- Token → 撤回，使用临时 token
- IP 地址 → 评估是否为内网地址
- Email → 评估是否为个人邮箱

**触发条件**: 检测到疑似敏感信息（弱规则）

**问题**: 疑似检测到敏感信息：${pattern}。是否确认提交？

**选项**:
- **撤回文件**: 撤回此文件，检查后重新提交
- **继续提交**: 确认非敏感信息，继续
- **查看上下文**: 显示匹配内容

---

### 3. 拆分决策（多层面）

**触发条件**: 检测到应用层 + 基础设施层混合变更

**场景**: 同一 refactor 意图，但跨越应用层和基础设施层，且无强依赖

**问题**: 检测到应用层和基础设施层混合变更，如何提交？

**选项**:
- **按层面拆分（推荐）**: 先应用层，后基础设施层
- **合并为单个**: 所有变更合并为 1 个提交
- **自定义方案**: 手动指定如何拆分

**层面定义**:
- **应用层**: `.java`, `.py`, `.ts`, `.js`, `.go`, `.rs` 等业务代码
- **基础设施层**: `Dockerfile`, `docker-compose.yml`, `.github/` 等部署配置
- **配置层**: `*.yml`, `*.yaml`, `*.toml`, `*.json`, `config/` 等应用配置
- **文档层**: `*.md`, `*.txt`, `docs/` 等文档

---

### 4. 拆分决策（多模块）

**触发条件**: 检测到多个模块的不相关变更

**场景**: 同一 feat/fix 意图，但跨越多个不相关模块

**问题**: 检测到多个模块变更：${modules}。如何提交？

**选项**:
- **按模块拆分（推荐）**: 每个模块独立提交
- **合并为单个**: 所有变更合并为 1 个提交
- **选择性拆分**: 指定哪些模块合并，哪些拆分

**模块识别**:
- 使用 `module_map` 配置识别模块
- 默认按目录结构识别

---

### 5. 拆分决策（3+ 提交）

**触发条件**: 检测到多个层面或模块，需要拆分为 3+ 提交

**场景**: 同时有应用层、基础设施层、文档层变更

**问题**: 检测到多层面/多模块变更，建议拆分为 ${n} 个提交：${commit_list}。确认方案？

**选项**:
- **确认拆分**: 按建议拆分为 ${n} 个提交
- **合并部分**: 选择性合并某些提交
- **全部合并**: 合并为 1 个提交
- **自定义**: 手动指定拆分方案

**示例**:
```
Commit 1: refactor(service): add logCommand parameter
  Files: 2 (应用层)

Commit 2: refactor(docker): optimize health check
  Files: 3 (基础设施层)

Commit 3: docs: update API documentation
  Files: 1 (文档层)
```

---

### 6. Breaking Change 确认

**触发条件**: 检测到破坏性变更

**场景**: API 接口不兼容、函数签名变更、公共字段删除等

**问题**: 检测到可能的 Breaking Change：${description}。确认吗？

**选项**:
- **确认（添加 !）**: 在 type/scope 后添加 `!` 标记
- **否，普通提交**: 不添加 `!` 标记
- **查看详情**: 显示检测到的破坏性变更

**Breaking Change 指标**:
- ❌ 删除公共 API/函数/字段
- ❌ 修改函数签名（参数/返回值）
- ❌ 修改响应格式结构
- ❌ 修改配置文件格式
- ❌ 删除配置选项
- ⚠️ 行为变更（可能需要）

**格式**:
```
feat(api)!: change response format to camelCase

BREAKING CHANGE: Response now uses camelCase instead of snake_case.
Consumers must update accordingly.
```

---

### 7. Hunk-Level 拆分

**触发条件**: 同一文件的不同变更需要不同提交

**场景**: 同一个文件中，一部分是 feat，另一部分是 fix

**问题**: 文件 ${file} 包含多个意图的变更，需要按 hunk 拆分。确认吗？

**选项**:
- **确认拆分**: 按变更意图拆分为多个提交
- **合并为单个**: 所有变更合并为 1 个提交
- **查看 hunk**: 显示各个变更块

**执行方式**:
使用 `git add --patch` 或 `git add -p` 交互式添加特定 hunk：
```bash
git add -p <file>
# 选择 y (add this hunk) 或 n (don't add)
```

---

### 8. Dry-Run 预览确认

**触发条件**: `--dry-run` flag present

**场景**: 用户预览提交计划，未实际执行

**问题**: Dry-run 预览完成，计划创建 ${n} 个提交。是否执行？

**选项**:
- **执行提交**: 按计划执行所有提交
- **调整方案**: 修改拆分或 commit message
- **取消**: 不执行，返回命令行

**预览内容**:
```
=== 计划的提交 ===

Commit 1: ${type}(${scope}): ${subject}
  Files: ${n}
  - ${file_list}

  Message:
    ${commit_message}

  将执行: git commit --only <files> -m "<message>"

=== 敏感信息检测 ===
${sensitive_check_result}

=== 拆分建议 ===
${split_suggestion}

=== 质量检查 ===
${quality_check_result}
```

---

### 9. 多意图拆分

**触发条件**: 检测到多个不同的 commit type

**场景**: 同时有 feat + docs，或 fix + refactor

**问题**: 检测到多个意图：${types}。如何提交？

**选项**:
- **按意图拆分（推荐）**: 每个意图独立提交
- **合并为单个**: 所有变更合并为 1 个提交
- **选择性拆分**: 指定哪些意图合并

**Commit Type 优先级**:
1. **feat** - 新功能
2. **fix** - Bug 修复
3. **docs** - 文档变更
4. **test** - 测试变更
5. **ci** - CI 配置
6. **build** - 构建系统
7. **refactor** - 代码重构
8. **chore** - 其他杂项

**拆分规则**:
- ✅ 必须拆分: `feat` + `fix`, `docs` + `feat`
- ⚠️ 可以合并: `feat` + `refactor`, `test` + `feat`
- ❌ 不应该拆分: 同一 type 的紧密相关变更

## 通用交互原则

### 问题设计
- ❌ "请输入 1/2/3" - 数字选择不直观
- ✅ 使用 AskUserQuestion 工具，提供描述性选项

### 选项数量
- **最少**: 2 个（二选一）
- **推荐**: 3 个（提供折中方案）
- **最多**: 4 个（避免选择困难）

### 选项描述
- 必须说明选择此选项的**后果**
- 使用具体动词：拆分、合并、撤回、继续
- 简洁但完整（1-2 句话）

### "Other" 选项
- 所有 AskUserQuestion 自动提供 "Other" 选项
- 用户可输入自定义方案
- Model 根据用户输入调整计划

---

## 工具使用

### AskUserQuestion 参数

```yaml
questions:
  - question: 清晰的问题描述
    header: 简短标题（≤12 字符）
    multiSelect: false  # 通常为 false，除非多选场景
    options:
      - label: 选项名称
        description: 选项描述（1-2 句话）
```

### 最佳实践

1. **问题要具体**: 不要问 "如何处理？"，要问 "检测到 X，如何处理？"
2. **标题要简短**: 使用 "拆分决策"、"敏感信息检测" 等简短标题
3. **推荐方案放在第一位**: 如 "按层面拆分（推荐）"
4. **提供取消选项**: 让用户可以中止操作
5. **处理 "Other" 选择**: 用户可能输入自定义方案
